# Soot — Authorization Policy Specification

**Status:** Draft v1 (2026-04-29)
**Audience:** Implementers landing per-library Actor modules, default
policies, test helpers, and CI guards across the soot ecosystem. Read
alongside `SPEC.md` (overall framework), `GENERATOR-SPEC.md` (what
installers scaffold), and `INTEGRATION-SPEC.md` (mTLS / endpoint
contracts).

## 1. Purpose

Today the soot libraries delegate authorization entirely to operators
*and* paper over the gap with `authorize?: false` in production code.
Every device-facing entry point (enroll, ingest, registry sync,
publisher, CRL publish, certificate issuance) currently bypasses Ash
policies. This means:

- An operator who adds a policy to an overridden resource has it
  silently bypassed by the library that calls into the resource.
- There is no defense in depth — the entire trust model collapses to
  "the mTLS plug ran".
- `authorize?: false` is the single most copy-pasted construct in the
  libraries; it has become the path of least resistance instead of an
  explicit, justified escape hatch.

This spec eliminates `authorize?: false` from non-test library code,
introduces an explicit actor model, ships default policies that pin
that model in place, and provides test helpers + a CI guard that keeps
the convention from regressing.

## 2. Principles

1. **Every Ash call has an actor.** Production library code never
   passes `authorize?: false`. If a call is internal sync that has no
   user, it gets a `System` actor with a named `:part` describing what
   it is doing.
2. **Devices are first-class principals.** A connected, enrolled
   device flows into Ash as a `Device` actor — not a certificate
   struct. Cert verification is a credential check; the resulting
   actor is the principal policies reason about.
3. **Default deny.** Resources ship with `policies` blocks; absent a
   matching `authorize_if`, the call fails. Operators add roles, not
   the absence of a policy.
4. **Tests use real policies.** Test helpers (`as_device`,
   `as_system`, `as_user`) make the actor explicit. Setup fixtures
   may use `authorize?: false` (matching upstream Ash convention),
   but the actions under test must run with a real actor.
5. **Bypasses are linted, not free.** A credo check refuses
   `authorize?: false` outside an allowlist (test/, priv/repo/seeds/,
   scripts/, and lines explicitly tagged `# authorize-bypass: <reason>`).
6. **Igniter wires this for free.** `mix <lib>.install` generates an
   `<App>.Actors` module, default policies on library-owned resources
   (overridable in the operator's app), and the credo rule.

## 3. Actor Model

Three actor kinds. Operators may add their own by following the same
shape.

### 3.1 `Device`

A row in `soot_core`'s `Device` resource. Carries `:id`, `:tenant_id`,
`:state` (`:bootstrap | :operational | ...`),
`:operational_certificate_id`, `:fingerprint`, `:label`, plus the same
helper fields the cert-derived actor exposes today (`:san`,
`:subject_dn`).

Created by `SootCore.Plug.MTLS.Resolver` (extends `AshPki.Plug.MTLS`):

```elixir
plug AshPki.Plug.MTLS, on_success: {SootCore.Plug.MTLS.Resolver, :resolve_device}
```

The resolver loads the `Device` row matching the verified cert and
puts it in `conn.assigns.actor` (a stable conventional name — Phoenix
authentication uses `:current_user`; we use `:actor` because it is
domain-agnostic). The cert-derived `AshPki.Plug.MTLS.Actor` remains
available at `conn.assigns.ash_pki_actor` for endpoints that need raw
cert data (enrollment, where the device row may not yet have an
operational cert).

### 3.2 `System`

A struct describing an internal subsystem performing an action with no
end-user. Defined per-app:

```elixir
defmodule MyApp.Actors do
  defmodule System do
    defstruct [:part, :tenant_id]
    @type part ::
      :enroller
      | :batch_provisioner
      | :crl_publisher
      | :issuer
      | :trust_loader
      | :mtls_resolver
      | :registry_sync
      | :publisher
      | :metric_monitor
      | :device_shadow_writer
  end

  def system(part) when is_atom(part), do: %System{part: part}
  def system(part, tenant_id), do: %System{part: part, tenant_id: tenant_id}

  def device(%MyApp.Device{} = d), do: d
end
```

`:part` is a closed set of atoms enumerated by the libraries that
mint them. The `<App>.Actors.system/1` constructor is what library
code calls — operators don't write `%System{...}` literals.

### 3.3 `User`

The admin / API actor produced by `ash_authentication` (or whatever
auth path the operator uses). `soot_admin` policies require a `User`
actor with a matching tenant + role. Out of scope for this spec
beyond saying: User actors exist and `<App>.Actors.user/1` returns
them.

### 3.4 Per-app `Actors` module

Each operator app gets one `<App>.Actors` module, generated by
`mix soot.install`. Library code never references `MyApp.Actors`
directly; it goes through configured factory functions on the library
config (same pattern soot already uses for `SootCore.device()` etc.):

```elixir
config :soot_core,
  device: MyApp.Device,
  actors: MyApp.Actors
```

Then `SootCore.actors().system(:enroller)` from inside `soot_core`.

## 4. Default Policies

Each library's resources ship with a `policies do` block. The block
is overridable: the operator's resource module can `use` the library
resource, then redefine `policies` to layer additional rules. Default
policies follow this shape:

```elixir
policies do
  # System actors permitted for this resource, by part
  policy actor_attribute_equals(:__struct__, MyApp.Actors.System) do
    authorize_if expr(^actor(:part) in ^@allowed_system_parts)
  end

  # Device actors for the device-owned subset
  policy action_type([:read, :update]) do
    authorize_if relates_to_actor_via(:device)
  end

  # Tenant scoping for everything else
  policy always() do
    authorize_if SootCore.Policies.SameTenant
  end
end
```

The exact `@allowed_system_parts` and device-relation predicates are
per-resource; they live next to the resource definition so the link
between "this code path is allowed" and "this resource" is local.

### 4.1 Per-library default-policy matrix

| Library | Resource | System parts allowed | Device-as-actor | Tenant scope |
|---------|----------|----------------------|-----------------|--------------|
| ash_pki | CertificateAuthority | `:trust_loader`, `:issuer`, `:crl_publisher` | n/a | n/a (global) |
| ash_pki | Certificate | `:issuer`, `:mtls_resolver`, `:crl_publisher` | own cert: read | yes |
| ash_pki | RevocationList | `:crl_publisher`, `:trust_loader` | n/a | n/a |
| soot_core | Tenant | `:enroller` (read only) | n/a | n/a (id is tenant) |
| soot_core | Device | `:enroller`, `:batch_provisioner`, `:mtls_resolver` | own row: read+update_state | yes |
| soot_core | EnrollmentToken | `:enroller`, `:batch_provisioner` | own token: read+consume | yes |
| soot_core | ProductionBatch | `:batch_provisioner` | n/a | yes |
| soot_core | SerialScheme | `:batch_provisioner` | n/a | yes |
| soot_core | DeviceShadow | `:device_shadow_writer` | own shadow: read+update | yes |
| soot_telemetry | StreamRow | `:registry_sync` | own active streams: read | n/a (global) |
| soot_telemetry | Schema | `:registry_sync` | own active schemas: read | n/a |
| soot_telemetry | IngestSession | `:registry_sync` | own session: read+record_batch | yes |
| soot_segments | SegmentRow | `:registry_sync` | n/a (read-only public) | yes |
| soot_segments | SegmentVersion | `:registry_sync` | n/a | yes |
| soot_contracts | BundleRow | `:publisher` | own bundle (active version): read | yes |

The Device-as-actor entries are the policies that let device-initiated
work flow without manual operator policies — exactly the user
requirement: "if a device has been authed as part of the connection it
should be allowed to push metrics and update its state".

### 4.2 Overriding in operator apps

When the operator overrides a library resource (e.g. `MyApp.Device use
SootCore.Device`), they get the default policy for free. They add
roles by extending the `policies` block:

```elixir
defmodule MyApp.Device do
  use SootCore.Device

  policies do
    # Operator-specific rules layered on top of library defaults.
    policy action_type(:destroy) do
      authorize_if {MyApp.Policies.AdminRole, role: :fleet_admin}
    end
  end
end
```

Ash policy composition is additive — library defaults still apply,
operator additions widen the allow set for their roles.

## 5. Test Helpers

`SootCore.PolicyCase` (and the per-library equivalents that wrap it)
provide:

```elixir
use SootCore.PolicyCase

test "device can update its own shadow" do
  device = factory(:device, tenant_id: t.id)
  shadow = factory(:device_shadow, device_id: device.id, tenant_id: t.id)

  assert {:ok, _} =
    as_device(device, fn actor ->
      MyApp.DeviceShadow.update_value(shadow, %{key: "label", value: "new"}, actor: actor)
    end)
end

test "device cannot update another device's shadow" do
  device_a = factory(:device, tenant_id: t.id)
  device_b = factory(:device, tenant_id: t.id)
  shadow_b = factory(:device_shadow, device_id: device_b.id, tenant_id: t.id)

  assert {:error, %Ash.Error.Forbidden{}} =
    as_device(device_a, fn actor ->
      MyApp.DeviceShadow.update_value(shadow_b, %{key: "label", value: "x"}, actor: actor)
    end)
end

test "registry sync may upsert a stream" do
  assert {:ok, _} =
    as_system(:registry_sync, fn actor ->
      SootTelemetry.Schema.create(:vibration, 1, "fp", %{}, actor: actor)
    end)
end

test "an unrelated system part may not write streams" do
  assert {:error, %Ash.Error.Forbidden{}} =
    as_system(:metric_monitor, fn actor ->
      SootTelemetry.Schema.create(:vibration, 1, "fp", %{}, actor: actor)
    end)
end
```

Helpers:

- `as_actor(actor, fun)` — invokes `fun.(actor)`. Trivial pass-through;
  exists so test bodies read uniformly.
- `as_device(device_or_id, fun)` — resolves to a `Device` struct (loads
  via factory if id passed) and calls `fun.(device)`.
- `as_system(part, fun)` / `as_system(part, tenant_id, fun)` — builds
  `%<App>.Actors.System{part: part}` and calls `fun`.
- `as_user(user, fun)` — same pattern for admin tests.
- `assert_forbidden(fun)` — helper that asserts `fun.()` returns
  `{:error, %Ash.Error.Forbidden{}}` (or raises the bang variant).

These live in each library's `test/support/` and in a shared
`SootCore.PolicyCase` that the others depend on for the actor module
contract.

### 5.1 What about Ash's own `authorize?: false` in tests?

Allowed, but **only** in test fixture / factory setup that creates the
preconditions for a test, not in the action under test. Concretely:

- `test/support/factories.ex` — yes (mirrors ash_authentication's
  `Example.User |> Ash.create!(authorize?: false)` pattern).
- `setup` blocks that seed rows the test will then act on — yes.
- The `assert {:ok, _} = MyResource.action(..., actor: actor)` line
  itself — **no**. The action under test always runs with a real
  actor.

The credo guard (Section 7) is configured to allow `authorize?: false`
under `test/support/` but flag it elsewhere in test files unless
tagged.

## 7. CI / Lint Guard

A custom credo check enforces no-bypass-in-lib:

```elixir
# in <repo>/lib/<lib>/credo/checks/no_authorize_false.ex
defmodule SootCredo.NoAuthorizeFalse do
  use Credo.Check,
    base_priority: :high,
    category: :warning,
    explanations: [
      check: """
      `authorize?: false` bypasses Ash policies. It is allowed only in
      test/support, priv/repo/seeds, scripts/, and on lines tagged
      with `# authorize-bypass: <reason>`. Replace with an explicit
      actor (Device, System, or User).
      """
    ]

  # ... scan source: flag occurrences of `authorize?: false` unless
  # the file path matches an allowlist OR the same line carries the
  # `# authorize-bypass: ...` comment.
end
```

The check ships in a small umbrella `soot_credo` package depended on
by every library's dev/test deps, alongside the existing
`{:credo, "~> 1.7", only: [:dev, :test]}` block defined in the
working-directory CLAUDE.md.

`mix precommit` adds `mix credo --strict` (already there); the
NoAuthorizeFalse check is enabled by default.

Allowlisted paths:

- `test/**/*.exs` — fixture files
- `priv/repo/seeds/**/*.exs`
- `scripts/**/*.exs`
- `lib/**/demo/**/*.ex` (demo modules clearly named)

Tagged escape:

```elixir
# authorize-bypass: bootstrap CRL load runs before any actor exists
{:ok, all} = crl_module.for_ca(ca_id, authorize?: false)
```

The reason is required (regex enforces non-empty text after the
colon); the line is logged in CI summary so we can audit them.

## 8. Igniter Generation

`mix soot.install` (or `mix <lib>.install` for partial setups)
produces:

1. `lib/<app>/actors.ex` with `System` struct, `system/1`, `system/2`,
   `device/1`, and a `user/1` stub (filled in by
   `ash_authentication.install`).
2. `config :soot_core, actors: <App>.Actors` (and equivalent for each
   library that needs it).
3. Per-resource override modules (`MyApp.Device`, `MyApp.Tenant`,
   `MyApp.Telemetry.StreamRow`, ...) that `use` the library resource
   and inherit its `policies`. The default policies from Section 4.1
   apply unmodified unless the operator extends them.
4. `test/support/policy_case.ex` re-exporting the helpers from
   `SootCore.PolicyCase`.
5. Credo config patch enabling `SootCredo.NoAuthorizeFalse`.

Flag: `--no-default-policies` skips steps 3-5 for operators who want
to bring their own auth design wholesale. This is escape-hatch
parity with `--no-example` and `--no-demo-seed`.

## 9. Phased Rollout

Each phase is one or more worktrees + PRs per repo, gated on green
CI.

- **P1 (soot_core)** — Add `SootCore.Actors` skeleton + `Device`
  actor + `SootCore.PolicyCase` helpers + factories using
  `authorize?: false` only in setup. No production behaviour change.
- **P2a (ash_pki)** — Convert all `authorize?: false` to system
  actors. Add default policies. Add the credo check (in-repo first,
  promoted to `soot_credo` later).
- **P2b (soot_core)** — Convert `enroll.ex` and `production_batch.ex`
  to system actors. Add default policies on Device / EnrollmentToken
  / Tenant / ProductionBatch / SerialScheme / DeviceShadow. Add the
  `SootCore.Plug.MTLS.Resolver` and update mount points.
- **P3 (soot_telemetry)** — `Device` actor flows through ingest.
  Default policies on Stream / Schema / IngestSession.
- **P4 (soot_segments + soot_contracts)** — System actors,
  default policies.
- **P5 (igniter installers)** — Each library's `*.install` task
  emits actors module patches, default-policy resource overrides,
  and credo config.
- **P6 (soot_credo)** — Extract the credo check into a shared dep,
  remove the per-repo copies, wire into every repo's `mix precommit`.
- **P7 (soot_admin)** — User actor + role-based policies on admin
  views (separate spec; out of scope here beyond the actor contract).

Each phase ships its own tests. No phase merges with `authorize?:
false` reintroduced into its own production paths — the credo check
turns red and CI blocks.

## 10. Out of Scope

- Multi-tenancy depth: the `SameTenant` filter check exists; this
  spec does not redesign it.
- ABAC / fine-grained roles for admin users — `soot_admin` will
  cover that. This spec only defines the Device + System contract.
- ash_jwt and ash_mqtt — neither has resources of its own to police.
  ash_jwt produces an actor for downstream policies (covered by the
  User contract). ash_mqtt generates broker config; broker-side ACL
  sync is its own work.
- Performance: `Device`-as-actor introduces a per-request DB lookup.
  P2b adds it to a connection-cached path so it amortizes; if profiling
  shows it as a hotspot, add an ETS cache keyed on cert id.
